# План: выразительная подача изображений без поломки rich-ui

Дата: 2026-11-01. База: 0.5.10, commit ee23461. Статус: план, реализация не начата.

## Цель и критерий результата

Подборка приложений должна показывать полезные широкие превью, читаемые описания и источники непосредственно в ответе. Несколько скриншотов одного приложения должны иметь удобный просмотр с отдельными подписями. Старые документы и компактные списки сохраняют поведение и внешний вид.

Ориентир пользователя: просторные строки ChatGPT с изображением слева, названием, полным описанием и источниками справа, разделителями без общей тяжёлой карточки. Не требуется буквальное воспроизведение размеров из скриншота: масштаб браузера неизвестен.

Не строить полный клон ChatGPT, не менять JSON-язык, не внедрять OpenUI как зависимость. Не добавлять произвольные CSS/JS/HTML, сетевой поиск изображений внутри рендерера или автоматический выбор оформления по словам в kind/title.

## Что уже есть

- grid + image + stack позволяют собрать изображение слева и текст справа без изменения схемы. Grid ограничен равными колонками; image имеет только src/alt/caption.
- entity-list жёстко компактен: 52×74px, описание ограничено двумя строками, источники и факты не выводятся в строке. thumbShape=square уже есть.
- EntityDetails показывает images:string[] по два изображения на страницу; свыше пяти страниц стрелки/счётчик, иначе точки. Отдельных подписей нет.
- Carousel принимает разные children, но фиксирует ширину элемента около 280px, поэтому не является готовой галереей полноразмерных скриншотов.
- Picture обеспечивает lazy loading и fallback, но размеры fallback задаёт вызывающий компонент.
- Промпт слишком категорично связывает коллекции с entity-list. Нужно сохранить обязательность богатой подачи там, где она полезна, но разрешить разные композиции.

Ключевые места: src/core/schema.ts; src/ui/RichResponse.tsx; src/ui/EntityDetails.tsx; src/ui/Picture.tsx; src/ui/rich-ui.css; src/host/tool.test.ts; prompt-rich-ui/prompt.md и references; tests/core/schema.test.ts; tests/ui/RichResponse.test.tsx; tests/ui/entityTab.test.tsx; tests/e2e/scenarios.spec.ts; src/demo/fixtures.ts.

## Этап 1 — просторный вариант существующего списка

### API

Добавить необязательное поле entity-list.layout: "compact" | "feature". Отсутствие эквивалентно compact. Это вариант существующей ноды, не новый тип сущности. Расширить существующий Entity.thumbShape значением "landscape" для скриншотов. Существующие poster/square и omission не переопределять: отсутствие остаётся poster. Feature управляет расположением и плотностью, thumbShape — форматом изображения. В примере приложений модель явно задаёт landscape.

Пример: {"type":"entity-list","layout":"feature","entityIds":["localsend","pika"]}.

### Представление feature

- На широкой области: превью примерно 160–220 CSS px, остальная ширина тексту; верхнее выравнивание. Это исходный диапазон для визуальной настройки, не жёсткое требование 216px из скриншота.
- Для thumbShape=landscape использовать ограниченную область около 4:3 и contain. Явный poster и отсутствие thumbShape сохраняют портретное соотношение. Не обрезать интерфейс ради заполнения рамки. Сохранить разумные отступы и нейтральный фон без двойной рамки.
- thumbShape=square остаётся квадратом для иконок. Не растягивать маленькую иконку как полноэкранный скриншот. Проверить оба варианта в fixture.
- Название, subtitle, полное description, badge, реальные ссылки sources. Не дублировать весь список facts: подробности остаются для расширенных данных.
- Тонкие разделители; без общего залитого контейнера компактного списка. Kind оставить второстепенным, не превращать в самый заметный заголовок.
- Нет изображения: текст использует доступную ширину, не оставлять пустой столбец. Ошибка загрузки: стабильная аккуратная заглушка, не сломанная геометрия.
- Не использовать одну большую button вокруг ссылок. Выделить кнопку открытия подробностей (заголовок/превью) и независимые ссылки источников. Не вкладывать интерактивные элементы друг в друга.
- Узкая область должна перестраиваться по ширине контейнера, а не только viewport: широкое окно с узким ответом/панелью — обязательный случай. Предпочесть container query с безопасной базовой раскладкой.
- На узкой области превью над текстом, с ограничением высоты; не раздувать квадратную иконку на всю ширину. Проверить 320/390/768 и широкие размеры.

Извлекать EntityList в отдельный файл только если это действительно уменьшает сложность. Не проводить попутную архитектурную чистку. Никаких :has-хаков, меняющих все row/image композиции.

### Проверки этапа

Валидация разрешает оба значения, отвергает неизвестное; документы без layout валидны. Проверить поведение кнопок и sources отдельно, клавиатуру, focus, отсутствие вложенных интерактивных элементов. Старые компактные snapshot должны остаться прежними. Добавить fixture приложений с широким скриншотом, квадратной иконкой, отсутствующим/сломавшимся изображением, длинным русским текстом и несколькими источниками. Тестовые картинки локальные и детерминированные; не зависеть от внешнего CDN в E2E. Существующий screenshot-loop пропускает listing: явно добавить baseline compact listing и новые feature/gallery сценарии. Проверить landscape во всех потребителях thumbShape (entity-ref, carousel, related, fallback): нигде не интерпретировать его случайно как poster. Новые размеры compact landscape описать явно, но старые poster/square не менять.

## Этап 2 — скриншоты с подписями

Делать после принятого визуального результата этапа 1. Не заменять автоматически существующую двухколоночную галерею постеров.

### Предлагаемый контракт

После независимой проверки обнаружен важный существующий путь: image-group уже использует ImageLightbox (src/ui/primitives/index.tsx), с навигацией, фокусом и тестами. Это сейчас текстовый триггер, не inline-галерея. Не добавлять параллельную ноду gallery: расширить image-group.

Сохранить legacy {type:"image-group",src:string[],alt:string,label?:string}. Добавить альтернативный items: MediaItem[] и presentation?:"button"|"gallery" (по умолчанию button). Ровно одно из src/items; alt остаётся доступным именем группы. MediaItem: {src:string,alt:string,caption?:string}. Не включать title/source без подтверждённой необходимости: подпись и существующие ссылки вокруг группы достаточны для первой версии.

Нормализовать legacy src и новые items в одном helper. Расширить существующий ImageLightbox под подписи и inline presentation, либо вынести общий viewer, не дублируя навигацию. Entity.images расширить до (string|MediaItem)[] только в этом же этапе, если действительно реализуются подписи внутри подробностей; старые строки остаются допустимы. Для явного режима одной картинки добавить Entity.galleryLayout?:"paired"|"single", omission=paired (старое поведение). Не выводить layout из типа картинки или наличия подписи. Entity.image остаётся превью списка, приоритет images над image сохраняется.

Пустые массивы отклонять для новых форм, а старые правила не ужесточать незаметно. До кодирования проверить LIMITS и задать единый ограниченный бюджет элементов. Проверить strict unknown keys, URL без credentials, строковые/массивные бюджеты. Новые формы описать discriminated union или однозначной runtime-проверкой; не разрешать src и items одновременно.

Это уточнение заменяет первоначальную идею отдельной gallery-ноды. Не строить второй lightbox. Для single-галереи использовать общий механизм выбранного элемента; legacy paired сохранять, а не насильно переписывать через single.

### Поведение

- Один кадр за раз, contain, стабильная область изображения, без автопрокрутки.
- Title/caption/source принадлежат текущему кадру. Общий текст сущности не меняется.
- Стрелки и счётчик, отключённые кнопки на концах, управление клавиатурой только внутри галереи. Не перехватывать стрелки глобально.
- По возможности свайп, но он не должен блокировать вертикальный скролл. Если жесты существенно усложняют код, сначала стрелки + клавиатура; явно отметить отсутствие свайпа, не объявлять его реализованным.
- Открытие оригинала обычной безопасной ссылкой с понятной подписью. Не делать новый modal/lightbox на этом этапе.
- Смена entity, уменьшение items и смена содержимого на том же id не оставляют индекс вне массива. Нет утечек между двумя галереями, вкладками и ветками conditional.
- Сначала новое изображение должно соответствовать новой подписи; старый кадр не остаётся визуально под новым текстом во время загрузки. Ключ кадра включает index+src (дубли URL с разными подписями допустимы). Проверить partial/streaming путь в src/host/partial.test.ts и native entity tab в tests/ui/entityTab.test.tsx. При использовании существующего lightbox из панели проверить Escape ownership и возврат фокуса. Fallback относится к конкретному src.
- Для 1 элемента не показывать бессмысленную навигацию; для большого числа не рисовать бесконечную ленту точек.
- Доступное имя, кнопки, счётчик aria-live без повторного чтения всей галереи. Не навешивать сложную ARIA-семантику без реализации клавиатурного поведения.

Тесты: 1/2/много кадров, дубли src, длинная подпись, разные соотношения сторон, загрузка/ошибка, сужение items, смена entity, две галереи одновременно, клавиатура и ссылки. Старые Entity.images и существующие тесты галереи остаются без изменения ожиданий.

## Этап 3 — промпт и примеры

Не раздувать always-on prompt. Заменить существующие формулировки выбора поверхности, а не дописать ещё один противоречащий блок.

- Коллекции остаются rich-ui по умолчанию, но допускаются entity-list, carousel/entity-ref и подходящая композиция существующих узлов.
- compact: быстрый список, постеры, небольшие иконки; feature: подборка с информативными широкими превью и пояснением прямо в ответе.
- Несколько изображений одного объекта: gallery; разные кандидаты: список, не один скрывающий всех слайдер.
- Не выдавать промокартинку или иконку за скриншот. Не придумывать URL, не трактовать скриншот другой ОС как доказательство вида на Linux. Если превью нет, убрать картинку, не подставлять случайную.
- gallery нужна для задачи, а не обязательна для каждого приложения. Подписи описывают видимое и подтверждённое.
- Сохранить локальный валидатор, stop rules, требования безопасности и бюджет секции <1250 слов. Проверить host leading line и tool description на противоречия.
- Обновить справочник и валидируемые примеры: compact; feature; inline gallery; entity.gallery; обычный короткий ответ без UI.

## Этап 4 — приёмка

1. До изменений запустить текущие build/unit/browser проверки и записать реальный baseline. Не переносить старые числа тестов как свежий результат.
2. Узкие unit/schema тесты после каждого этапа.
3. npm run build; npm run build:plugin; npm test; npm run test:browser. Команды определены в package.json. Проверить доступность зависимостей/браузерного контейнера, не ставить новую среду без необходимости.
4. Визуальная матрица: светлая/тёмная темы; 390 и 1280px; узкий контейнер внутри широкого viewport; длинный текст; missing/error image; feature list; inline и detail gallery; старый films compact.
5. Не обновлять все snapshots вслепую. Для новых — создать и открыть картинки; для изменённых старых — объяснить каждую разницу. Нежелательный diff старого compact блокирует завершение.
6. Axe + keyboard: открытие/закрытие подробностей, возврат фокуса, независимые source links, галерея, отсутствие горизонтального overflow.
7. Поведенческие прогоны в свежем контексте с актуальным промптом: подборка Linux-приложений с превью; фильмы; просьба показать несколько экранов приложения; сравнение двух UI; короткий факт; код. Сохранить запросы, сырой ответ, результат валидатора и краткую оценку выбора layout. Не гонять до первого успеха и скрывать неудачи.
8. Критерий успеха: валидность и правильный выбор подачи, а не наличие gallery в каждом ответе. Рендер-тесты не заменяют проверку модели.

## Доставка и границы задачи

Текущая просьба — подготовить план, не реализовывать и не публиковать. Следующий исполнитель сначала читает этот документ и проверяет git status: не затрагивать чужие изменения.

После отдельного запроса на реализацию: выполнить этапы, обновить README/QUALITY/PARITY по фактическим результатам. Не заявлять полный паритет с OpenAI. Если запрошен выпуск и активация — следовать существующему npm/Nix процессу, выбрать версию после проверки реестра; обновить декларативные pin/hash, проверить активированный сервис и текущий GUI. Новая схема обязана быть установлена до демонстрации новых блоков в живом чате. Старый установленный валидатор новые поля отвергнет.

Не запускать заменяющий GUI-сервер. Изолированное demo/E2E не доказывает, что текущая страница DSH обновлена. После активации нужен runtime smoke test. Свежий чат нужен для актуального системного промпта.
